 ABOUT THIS FILE
 --------------------------------------------------------------------------
 The program is bilingual, so the changelog is too. This is the English
 edition; `Changelog.txt`, next to it, is the Portuguese one.

 The two are NOT identical, and that is on purpose. The Portuguese file is
 the project's working record - it carries every version since 1.4, with the
 reasoning, the measurements and the mistakes written out at length, because
 that is where the project remembers why it did things. This file covers the
 CURRENT release in full and summarises what came before. If you need the
 archaeology of an old decision, the Portuguese file is where it lives.

 EVERYTHING THAT CHANGED SINCE 1.9.3 (last public release, 15/09/2026).

 8. Window/installer: toolbar in work order, F3/F4 with a brake; reading,
    measuring and census run as separate jobs; installer asks the language
    and shows the EULA; PT/EN translation closed; installer runs in
    64-bit mode; uninstall no longer leaves _logs and icone behind; blank
    taskbar icon fixed (installer removes the old per-user Start Menu

 9. Tools: seconv, mkvextract and three DLLs removed. mkvmerge 102.0,

 INSTALLER 2.0.4  -  22/09/2026    *** THE QUESTION COMES BEFORE THE WORK ***
==============================================================================
 Components: ENGINE 14.8 | WINDOW 19.4 | CORRECTOR 2.28 | TESTAR_LAFIRMA 4.4

 1. CANCEL DID NOT STOP THE HANDOVER BETWEEN STAGES
 --------------------------------------------------------------------------
 He pressed [ESC] and the engine went on to build the WHOLE final MKV - 19
 GB, 1m42 - only to DELETE it immediately after. 104 seconds of work started
 after the stop request.

 And the guard existed. It sat at the END of the episode, with a comment
 naming the exact problem: "if ESC is pressed between two stages, neither
 fails - without this guard the episode would be recorded as finished". It
 protected the RECORD, not the user's TIME. Asking "was it still worth it?"
 after doing the work is bookkeeping, not cancelling.

 2.0.3 put the question in the three OCR fallbacks because that is what that
 day's log showed. I did not go looking for the other doors, and the next
 door was the biggest of all. A wrong pattern is fixed where it LIVES, not
 only where it hurt.

 Now EVERY stage asks on entry, and the test suite checks the question stage
 by stage - and that it comes BEFORE each stage is announced.

 2. THE CENSUS CHANGED THE COLOUR BELOW AND LEFT THE ONE ABOVE
 --------------------------------------------------------------------------
 After the census the diagnosis line turned orange and the DOLBY VISION
 column stayed RED - the same screen saying two things about one file. In
 the log there is not a single queue-repaint line between the census
 finishing and his next action.

 2.0.2 made the column and the diagnosis ask the SAME function for the
 colour, and I treated that as solved. It was not: both ask the same way,
 but only one was asked AGAIN. One owner of a rule is worthless if half the
 screen never consults it again.

 The lesson was already written one branch below in the same file: "new
 state without a redraw is the screen lying."

 3. CHECKED AND CORRECT
 --------------------------------------------------------------------------
 * The GoT subtitle came out CLEAN - all 37 proper nouns intact. The 2.28
   guards held, and the legitimate fixes still happened.
 * No corrector report is produced when the subtitle scores EXCELLENT: the
   engine deletes the working files on purpose. That is the cleanup, not a
   failure.
 * The census is 2.2x faster with 2.0.3: the same file went from 196.0s to
   89.5s, and the estimate was off by 5%.

 INSTALLER 2.0.3  -  22/09/2026    *** CANCEL IS A STATE, NOT AN EVENT ***
==============================================================================
 Components: ENGINE 14.7 | WINDOW 19.3 | CORRECTOR 2.28 | TESTAR_LAFIRMA 4.3

 Everything in this version came out of ONE user test session. Nothing here
 was hunted for by us: all four were in the log and the report he sent.

 1. [ESC] WAS NOT READ BY THE OCR FALLBACK CHAIN
 --------------------------------------------------------------------------
 Four lines of his log tell the whole story: the cancel killed seconv at
 11:57:31, the step read that death as "seconv failed", and the safety net
 started PgsToSrt from scratch - 90 seconds - and then called the corrector,
 which calls seconv again for its second opinion. THREE programs started
 after the user said stop. He had to close the window by hand.

 The cause is not the killing - it is the READING of the result. From below,
 "I killed the tool" and "the tool failed" look identical: no file came out.
 And the honest reaction to a failure is to try the backup. The question that
 comes before that one was missing.

 There is now ONE place that answers "is there still a point in starting?"
 and all three fallbacks ask before starting. The question comes before the
 sub-step is announced, too - announcing a step that will not run leaves a
 phantom step on the bar, which is exactly what he sat watching.

 > LESSON 50: CANCEL IS A STATE, NOT AN EVENT. Whoever has a plan B must ask
 > whether there is still a POINT, before asking whether it worked.

 2. "seconv DID NOT PRODUCE A SUBTITLE" WHEN THE TRUTH WAS "I KILLED IT"
 --------------------------------------------------------------------------
 Same family, on the text side. When the shutdown was the cancel, the line
 now says so. A third state needs a name.

 3. THE SECOND [ESC] WAS REFUSED WITH "DOES NOT APPLY TO STATE 'RUNNING'"
 --------------------------------------------------------------------------
 The state WAS running, and it was true - and it was useless. Same defect F11
 had before 18.22, back through another key. The refusal now names the real
 reason: either the cancel was already requested N seconds ago and is in
 progress, or there is no conversion to cancel.

 4. THE CORRECTOR WAS INVENTING PROPER NOUNS
 --------------------------------------------------------------------------
 From the corrector report he sent: 'All Spark' became 'Ali Spark' five
 times, 'Tut' became 'Tui', 'Autobotzinho' became 'Autoboizinho'. The OCR had
 got all three RIGHT. We broke them - and much of the "13 OCR errors" 2.0.1
 counted in that subtitle was our own work.

 The letter-swap rule (l/t/| to i) was the ONLY rule in the corrector that
 did not receive the proper-noun list. And the list would not have saved it
 anyway, because the two ends asked with different functions: the harvester
 asks one that finds "all" in the 1.3M dictionary and concludes "known word,
 needs no protection", while the rule asks one that, under 4 letters, does
 not consult that dictionary at all and concludes "never seen it" - then
 swaps l for i, finds "ali", a legitimate Portuguese word, and rewrites.

 Two functions answering the OPPOSITE about the same word, with the
 protection depending on one and the damage on the other.

 Three fixes: the rule receives the list; the harvester asks with the SAME
 function the rules use; and two guards that depend on no dictionary at all -
 a capitalized word next to another capitalized word is a name, and a
 capitalized word in the MIDDLE of a sentence does not get letters swapped.

 THE PRICE OF THE THIRD GUARD IS MEASURED AND WRITTEN IN THE CODE: in his
 real report, this rule's changes to mid-sentence capitalized words were 1
 correct fix against 7 corruptions. Losing the one fix is the right price:
 not fixing is doing nothing; swapping a proper noun for another word is
 handing back a file that is WORSE than it arrived, silently.

 5. THE CENSUS MINUTE THAT NO CLOCK WAS MEASURING
 --------------------------------------------------------------------------
 Both census clocks stopped before the L1_export.csv was read: 53s uncounted
 on one file, 107s on another. The second had FEWER frames and took TWICE as
 long - because the cost was Select-Object -Unique, which compares every row
 against every unique row kept so far. It became a single HashSet pass, and
 its time now counts: time no clock measures cannot feed the estimate, which
 is why the estimate kept falling short no matter how it corrected itself.
 The same pattern was replaced in the sample measurement, where the CSV is
 small and the cost did not show.

 6. THE SUBTITLE VERDICT SENTENCE, AGAIN
 --------------------------------------------------------------------------
 The 2.0.1 one said the right thing badly. Same content, two clauses:
     "No detectable defects. The counter does not catch a swapped proper name."

 INSTALLER 2.0.2  -  22/09/2026      *** RED GAINED A STEP ***
==============================================================================
 Components: ENGINE 14.61 | WINDOW 19.2 | TESTAR_LAFIRMA 4.2 | CLICK BENCH 4.0

 1. COMPLEX FEL IS NO LONGER A SINGLE RED
 --------------------------------------------------------------------------
 The rule that painted a file red was one line: the peak of the brightest
 scene against the peak of the mastering display. ONE scene above it turned
 the whole file red - and red, in this program, means "this is the case that
 ruins the picture".

 The two cases we have MEASURED:

     Saving Private Ryan   216 of 1,124 scenes (19.22%)  peak 3,468 / master 1,000
     Transformers ROTF      15 of 2,225 scenes ( 0.67%)  peak 1,555 / master 1,000

 The community spreadsheet measures the second one by a different route
 (madVR, on the decoded image) and reports 0.3% of FRAMES above 1,000 nits -
 with the SAME frame count as our census, 215,617. Both measurements agree
 that this film barely touches above the master. It was getting the same
 colour as a film that expands brightness all the way through.

 A comment from 16.85 had already written what was missing - "an isolated
 peak in one scene is a different thing from half the film above the ruler" -
 and 16.87 explained why the sample could not answer it: 3 to 4 scenes are
 not statistics. The FULL CENSUS is that condition met: it reads the whole
 film.

 NOW: with the census in hand, red steps down to ORANGE when BOTH guards pass
 at once -

     1. FREQUENCY   under 1% of the film's scenes
     2. OVERSHOOT   the peak is no more than TWICE the master

 Two on purpose. Half a dozen scenes asking for 4,000 nits on a 1,000-nit
 master is rare AND severe - frequency alone does not describe that. The same
 20-scene floor the suspicious-ruler check already used applies: a percentage
 of 5 scenes is not a percentage.

 WHAT DOES NOT CHANGE, AND THE LOG SAYS SO: the layer is NOT reclassified.
 FEL is still FEL, the EL is still discarded, the fine residual is still
 lost. What changes is SEVERITY, which is what the colour communicates. That
 is why the destination is orange - the colour of "converts, with a caveat" -
 and NEVER green.

 The numbers (1% and 2x) are a convention anchored on two measured cases, and
 they are written in the code on purpose so they can be argued with instead of
 becoming folklore. Two points are not a curve.

 Column colour and diagnosis colour come from the same function - two parts
 of the screen deciding the same colour by different rules was a defect here
 before (16.84). The cache keeps the result, so re-reading the folder does
 not resurrect the red of a file whose census already proved otherwise.

 2. THE ENGINE NOW SAYS ITS OWN MEASUREMENT IS A SAMPLE
 --------------------------------------------------------------------------
 The engine measures again at conversion time, by sample: it knows SOME scene
 exceeds the master, not how many. So the window could say orange while the
 engine log said "CONVERSION NOT RECOMMENDED" for the same file. They are not
 fighting - they are measurements of different sizes - and the engine now
 says so instead of letting the user discover the divergence alone.

 3. CHECKED BY SABOTAGE
 --------------------------------------------------------------------------
 Eleven sabotages, eleven caught. Test suite 1,187 tests, click bench 336
 invariants.

 4. THE TEST SUITE NOW CHECKS ITS OWN ENCODING
 --------------------------------------------------------------------------
 It demanded CRLF from everything in fonte\ and never checked the one .ps1 it
 cannot reach: itself. It had three stray LFs. No damage - but a file that
 demands of others what it does not meet is the worst place for an exception.

 INSTALLER 2.0.1  -  22/09/2026      *** THE NAME SAYS WHAT THE FILE IS ***
==============================================================================
 Components: ENGINE 14.6 | WINDOW 19.1 | TESTAR_LAFIRMA 4.1 | CLICK BENCH 4.0

 1. THE [BL+RPU] STAMP IN THE FINAL FILE NAME
 --------------------------------------------------------------------------
 Every .mkv this engine produces is single-layer BL+RPU video: either
 dovi_tool converted Profile 7 (MEL/FEL) to 8.1, or the file already was
 Profile 8.x with no Enhancement Layer. Files with no Dolby Vision are
 skipped at diagnosis, and Profile 5 leaves through another door, as .mp4.
 So the stamp holds for every .mkv the engine writes - and it is now in the
 name:

     Movie.2009.2160p.REMUX-GROUP [BL+RPU].mkv

 THE "ALREADY EXISTS IN THE OUTPUT FOLDER" GUARD NOW CHECKS BOTH NAMES.
 Everything converted before this version is stored under the OLD name, with
 no stamp. Had the guard looked only at the new name, an entire library
 would be reconverted from scratch on the first queue after updating - and
 the good output overwritten at the end. The engine tests the new name AND
 the old one, and the log says which of the two it found.
 The stamp is never doubled: reconverting an already stamped file does not
 produce "Movie [BL+RPU] [BL+RPU]".
 The loose subtitle copy (.srt) and the log copy follow the new name, so the
 player still matches the external subtitle to the movie.

 2. THE CENSUS ESTIMATE ONLY LOOKED AT THE CPU
 --------------------------------------------------------------------------
 Measured from the user's own logs:

     Saving Private Ryan   82 GB / 2h49  on SSD  ->  sample x 4.7
     Transformers ROTF     78 GB / 2h30  on HDD  ->  sample x 85.5

 Same file size, factor 18 times apart. The CPU did not change - the DISK
 did. The full census reads the WHOLE movie; on a mechanical drive the clock
 is owned by reading, not by processing.
 The estimate now computes both times - disk (file size over the measured
 source speed) and CPU (movie duration times the learned seconds-per-second)
 - and takes the LARGER. The log says which one won. Checked against the
 real logs: 1% error on Ryan, 22% on Transformers, against 1,700% for the
 old model.
 Learning is guarded too: the seconds-per-second figure is only re-adjusted
 when the CPU owned the clock. Learning "0.0711 s/s" from a read that was
 held back by a slow disk taught the wrong lesson to the next movie, which
 may sit on an SSD.

 3. THE SUBTITLE VERDICT PROMISED TOO MUCH  (from 14.55)
 --------------------------------------------------------------------------
 "No faults found. This subtitle is good to watch." The arithmetic was
 right - 1 defect in 1,832 blocks is 0.055%, under the 0.1% that earns
 EXCELLENT. The SENTENCE was wrong. Measuring a real OCR output on the
 bench we found 13 human-visible errors the counter does NOT catch, because
 they are valid words in the wrong place ("Ali Spark" for "AllSpark", and
 others). The counter finds impossible characters and broken blocks; a
 swapped proper noun it does not find and never will.
 The sentence now says what the measurement covers:
     "No faults of the kinds I can detect. A swapped proper name is
      something I cannot catch - worth a quick look."

 4. TOOLS REMOVED FROM THE INSTALLER
 --------------------------------------------------------------------------
 mkvextract.exe, LIBCURL.DLL, nvcuda.dll and nvcuvid.dll were removed.
 Checked file by file: no .ps1 in the project calls any of the four.
 mkvextract stopped being used in 14.16, when video started being copied
 inside the container instead of extracted; the three DLLs came along with
 the mkvtoolnix package and were never called. Nothing breaks. All four were
 removed from the file trees in the documentation.

 Tools in this version:
     mkvmerge          v102.0
     ffmpeg / ffprobe  9.0.1-essentials
     MediaInfo CLI     v26.05
     dovi_tool         2.3.3  (minimum required since 1.8)

 INSTALLER 2.0 (first test build)  -  18/09/2026        *** THE VERSION THAT MEASURES WHAT
                                          IT PROMISES ***
==============================================================================
 Components: ENGINE 14.55 | WINDOW 19.0 | TESTAR_LAFIRMA 4.0 | CLICK BENCH 4.0

 This is the first version in which the ENGINE changes since 1.9.2 - and it
 changes little, on purpose. What really changes is the honesty of the numbers
 on screen.

 1. THE CALIBRATION THAT CANCELLED ITSELF OUT
 --------------------------------------------------------------------------
 Every session since 16.99 the program printed this line:

   CALIBRATION: runs spread 44% among themselves (0.0125 to 0.0180) ... the
   estimate will keep being wrong per file until the weights are revised.

 The diagnosis was right. The correction could never work, because since 16.64
 the calibration constant HAD NO EFFECT AT ALL. The algebra, with
 k = SegPorGbPorPeso:

   weight_i = round( s_i / (Gb * k) )
   est      = Gb * k * SUM(weight_i) = SUM( s_i )

 k cancels. Measured with the real numbers from Saving Private Ryan (81.99 GB):
 k = 0.0125 gives 3,665.0s; k = 0.0400 gives 3,666.6s. The constant varies by
 3.2x and the estimate moves 1.6 SECONDS out of 3,665 - which is the rounding
 of the weight to an integer, nothing else.

 THE FIX, AND WHY IT IS PER STAGE

 Calibration moved out of the weight calculation and now multiplies the
 predicted SECONDS - outside the loop, it cannot cancel itself. And it stopped
 being ONE number for the whole file: it is now ONE PER STAGE.

 That was the real reason for the 44%. A long, small TrueHD film and a short,
 large DTS film err in OPPOSITE directions, and a single scalar cannot describe
 both shapes at once. With a per-stage factor, "this machine is 30% slower on
 audio" stops fighting "this disk is 10% faster on remux".

 Learning COMPOSES instead of re-applying: the prediction carried in the batch
 already includes the current factor, so what gets stored is the composed
 factor. Storing the raw ratio would apply the correction again on the next
 batch, drifting further each run. The bench checks exactly that.

   LESSON 49: A NUMBER THAT APPEARS ON BOTH SIDES OF THE SAME EQUATION IS NOT
              AN ADJUSTMENT - IT IS A CHANGE OF UNIT. Before trusting a
              calibration constant, vary it and watch the result move.

 INSTALLER 1.8.4  -  11/09/2026     *** A SPACE IN THE FOLDER NAME ***
==============================================================================
 Components: ENGINE 14.52 | WINDOW 17.09 | SUBTITLE FIXER 2.27 | REOCR 1.29
             TESTAR_LAFIRMA 3.19

 THE RPU PIPE BROKE ON PATHS WITH SPACES  (14.52)
 --------------------------------------------------------------------------
   Bloodsport failed with a message that is not ffmpeg's: "The filename,
   directory name, or volume label syntax is incorrect" - that is cmd itself
   complaining about the line it was handed. Ryan and Troy always worked
   because they sit directly in ...\FILMESS\; Bloodsport sits in a folder
   whose name contains a space.

   THE CAUSE: the pipe was built as ONE STRING - four quoted paths inside an
   outer pair of quotes - and handed to "cmd.exe /c" as an argument.
   PowerShell 5.1 REWRITES quoting when passing arguments to a native
   executable, so with a path containing a space what arrives is no longer
   the line that was written. There is no "correct" quoting: the rewrite
   happens after us.

   THE FIX: the line stops travelling as an argument. It is WRITTEN to a
   .cmd file in the temp folder and cmd receives only that file's path - a
   single simple argument. The .cmd is written in ANSI (the code page cmd
   assumes; UTF-8 would break accented paths) and '%' is escaped as '%%'.

   This covers the full census and the bench - the only two places in the
   project that build a pipe through cmd. Normal conversion never did: it
   calls ffmpeg with an argument array, no cmd in between.

 AND BLOODSPORT ANSWERED THE HDR10+ QUESTION
 --------------------------------------------------------------------------
   Even with the RPU failing, the container read already gave the verdict:
   Bloodsport (52.47 GB, 1h32) - ruler 1000 nits from the frame SEI, and
   HDR10+ PRESENT. It is the first file we have measured carrying both Dolby
   Vision and HDR10+ in the same container. Ryan and Troy do not.

 0. THE LANGUAGE CHOICE ACTUALLY REACHES THE DISK  (17.02 / 14.48)
 --------------------------------------------------------------------------
   Three defects reported after using 1.8 as installed.

   1) "I OPENED IT IN ENGLISH, CLOSED IT, IT CAME BACK IN PORTUGUESE."
      16.93 saved the choice to IDIOMA.txt in the PROGRAM'S OWN FOLDER. That
      works when LaFirma lives in C:\LaFirma and fails SILENTLY when it lives
      in Program Files - Windows refuses the write and the catch swallowed
      the error. The choice never reached the disk.
      The program now tests the folder with a real write, not a guess based
      on the path. If it is writable, it keeps saving there. If not, it falls
      back to %LOCALAPPDATA%\LaFirma, which belongs to the user and always
      accepts. Reading looks in both places, and a failure is now written to
      the log - failing in silence was the defect.
      The timing calibration (16.99) wrote to the same place and had the same
      problem; it was fixed with it.

   2) "COMING BACK TO PORTUGUESE LOOKS WRONG."
      Switching language redraws what is built at runtime: the queue and the
      diagnosis. The DISK PANEL is built at runtime too and was not on that
      list, so it stayed in the previous language until the next folder read.
      Two languages on one screen - exactly what 17.01 had just fixed
      everywhere else. It now comes back with the rest.

   3) "MEASURING IS TAKING TOO LONG."
      True, and 14.47 is the cause: the sample went from 3 to up to 11
      points. It grew for one reason - the L1 census, which counts how many
      scenes ask for more brightness than the mastering display delivers.
      That census can only be done when the file DECLARES the master peak.
      Without that ruler nothing is counted, so the extra points were reading
      scenes nobody would count.
      Now: WITH a ruler, the full sample. WITHOUT one, three points - which
      is all MEL vs FEL needs, since el_type does not change across a film.
      No answer is lost; what goes is reading that was not becoming a number.
      And the time each measurement costs is now MEASURED and logged,
      alongside how many points were asked for and how many were read.

 1. MEL, SIMPLE FEL AND COMPLEX FEL - measured before converting
 --------------------------------------------------------------------------
   Up to 1.7.3, converting a Profile 7 always looked the same on screen. The
   program now reads the enhancement layer FIRST, through the RPU's el_type
   field, and separates three cases:

     MEL          green    the layer carries no picture; discarded losslessly
     SIMPLE FEL   orange   carries picture, but refinement only
     COMPLEX FEL  red      raises brightness - conversion not recommended

   What separates Simple from Complex is one number: the file's L1 against
   the mastering display peak. Without that peak declared, the program says
   it does not know instead of picking a side.

   Measured on the test machine: Troy 2004 is MEL (303 of 1,000 nits), GoT
   S08E01 is Simple FEL (153 of 1,000) and Saving Private Ryan is Complex FEL
   (1,608 of 1,000). The Ryan was found by measurement, from no list.

   Since 17.01 the scale is the same everywhere on screen: the [EL: ...] tag
   in the diagnosis, the DOLBY VISION column text and the row chip all read
   from one function. Before that the rule was written in one place and
   half-copied in the other, so the same measured verdict could come out in
   two different colours.


 2. WHY THE CAVEAT EXISTS, said precisely
 --------------------------------------------------------------------------
   This is the point most writing on the subject leaves vague:

   - dovi_tool in MODE 2, which is what this program uses, REMOVES the
     Profile 7 FEL luma/chroma mapping from the RPU - the part of the
     instructions that makes no sense without the second layer. What comes
     out is a legitimate Profile 8.1.
   - What NO dovi_tool mode does is RECOMPUTE L1. The per-scene brightness
     number stays whatever the original analysis measured, and that analysis
     looked at the picture with the EL added in.

   That, and only that, is where the Complex FEL caveat comes from. It is not
   a limitation of this program: it is the state of the tooling, and it is in
   dovi_tool's own documentation.


 3. dovi_tool 2.3.2 -> 2.3.3
 --------------------------------------------------------------------------
   Validated on a purpose-built bench: 5 files, 3 profiles, 2 CM versions,
   ZERO divergence in DM version, scenes, L1 MaxCLL, L1 MaxFALL and RPU
   bytes. 2.3.3 brings `export --levels`, used to read each scene's L1 and
   the active area (L5) in the same pass.

   Bench finding: on a valid HEVC cut in half, both versions exit with code 0
   and leave a partial RPU saying "Done." dovi_tool does not guard against a
   truncated file - the one that distrusts the output size is LaFirma.

   2.3.3 IS NOW THE MINIMUM. Earlier versions lack `export --levels`, and
   without it the program cannot measure MEL vs FEL.


 4. ACTIVE AREA (L5)
 --------------------------------------------------------------------------
   Read and checked against the real resolution, with the format named. It
   only reaches the screen when the declared border results in no cinema
   format at all - an RPU with the wrong crop, which came that way from the
   source.

   Checked against Dolby's own manual (Dolby Vision Professional Tools User
   Manual 5.4.0): the four L5 numbers are the LETTERBOX area, in the order
   left, right, top, bottom, and the active area is the resolution minus
   them - exactly how the program reads it. And the check the program runs
   mirrors a validation Dolby itself treats as a metadata ERROR: an aspect
   ratio declared in L5 that does not match the frame's.


 5. THE "LEARN" BUTTON - in both languages
 --------------------------------------------------------------------------
   Opens the full text about the conversion - 14 sections, from BL/EL/RPU to
   why the binaries are not on GitHub. It lives in FAQ_PT.txt and FAQ_EN.txt,
   outside the .ps1, so a sentence can be fixed without touching code.

   The file is chosen AT CLICK TIME, by the current language: switching the
   flag mid-session takes effect immediately, with no restart.

   Section 4 is the one that matters most and does not exist ready-made
   anywhere else: Shield, Apple TV, Zidoo, Dune and TVs already discard the
   EL, so on those devices Profile 7 already plays the way the converted file
   will. Who loses something is whoever has a dual-layer decoder. Without
   that, the red warning frightens more than it should.

   Section 14 is new: the sources behind every claim in the text - the
   repository, dovi_tool, Dolby's professional support, two community
   spreadsheets (measured brightness by title, and players with MEL/FEL
   support), a folder of FEL vs base layer comparisons, and DoViBaker.


 6. LANGUAGE: PORTUGUESE AND ENGLISH
 --------------------------------------------------------------------------
   A flag next to the Learn button. The translation is a layer on top - the
   program stays entirely in Portuguese if IDIOMA_EN.txt goes missing. The
   choice is remembered between sessions.

   Since 17.01 the translation also reaches text ASSEMBLED AT RUNTIME
   ("Queue (3)", "VIDEOS IN QUEUE (2 of 3 Selected)", "Converting - Step
   3/5", the whole diagnosis block), which used to stay in Portuguese on an
   English screen. IDIOMA_EN.txt accepts PATTERN RULES (a line starting with
   ~), so a new phrase needs a new line in the .txt, not new code.

   A trap worth knowing, because it bit once: the rules run IN ORDER. The
   generic "...Convertido -> ...Converted" matched "Já Convertido" first and
   returned the hybrid "Já Converted". More specific rules come first.


 7. PROFILE 5 -> MP4
 --------------------------------------------------------------------------
   Profile 5 cannot reach 8.1 without re-encoding the video, and re-encoding
   is exactly what this program refuses to do. But P5 no longer just sits
   there: what it needs is not a profile conversion, it is a container
   devices will read.

   The program now remuxes P5 to MP4 with the dvh1 tag, video COPIED frame by
   frame. Audio is copied when it fits in MP4 (E-AC-3, AC-3, AAC, MP3, ALAC,
   FLAC, Opus) and becomes E-AC-3 640k when it does not (TrueHD, DTS). Text
   subtitles become mov_text. PGS subtitles are discarded WITH A WARNING -
   image subtitles have no representation in MP4, and there is no OCR on this
   path.

   The output is verified by DURATION, not by size. Two attempts to verify by
   size failed on the first real test: a short clip legitimately weighs
   little, and a remux that drops the DTS track comes out much smaller than
   the source with nothing having gone wrong. Duration does not lie - a remux
   cut in half leaves a file that exists, opens, and lies about being
   complete. If it does not match, the .mp4 is deleted.


 8. THE TIME ESTIMATE CALIBRATES ITSELF
 --------------------------------------------------------------------------
   The first-second estimate was off by a lot and the bar jumped mid-run:

     Troy         predicted 1697s   real 1091s   +56%
     Se7en        predicted  910s   real  655s   +39%
     Spider-Man   predicted 1200s   real 1121s    +7%

   Changing the constant does NOT fix it - already measured: the average
   improves Troy and Se7en and makes Spider-Man UNDERESTIMATE by 20%. The
   problem was never the value: one fixed number has to serve different
   machines, disks and films.

   So it stopped being fixed. Every converted file appends a line to
   CALIBRAGEM.txt with what it actually cost per GB per weight unit, and the
   next estimate uses the p75 of the last five runs.

   WHY p75 AND NOT THE MEDIAN - the four options were run against the three
   real films:

     fixed 0.0153   mean error 33.8%   worst 55.5%   underestimates 0 of 3
     median         mean error 11.6%   worst 22.9%   underestimates 1 (-23%)
     p75            mean error 18.3%   worst 28.6%   underestimates 1 (-11%)
     maximum        mean error 25.0%   worst 45.3%   underestimates 0 of 3

   The median is the most accurate on average AND the one that errs worst
   where it hurts: it would promise Spider-Man 23% less time than it takes.
   Promising a time that will not be met is a message that lies.

   WHAT THIS DOES NOT FIX, written down so it does not become a promise: the
   three films are from the SAME machine and still spread from 0.0098 to
   0.0143. Much of the error is not the machine - it is the WEIGHT MODEL,
   which describes different films with the same shape. Calibration kills the
   systematic error; the per-file variation only goes away by revising the
   weights. When the spread exceeds 30%, the log says so rather than letting
   it look solved.

   Dirty history does not get in: a run cancelled halfway, or any figure
   outside the sanity limits (0.004 to 0.060), is refused with the reason in
   the log. A missing or unreadable file falls back to the factory number -
   nobody is left without an estimate for lack of history.


 9. DISK SPACE
 --------------------------------------------------------------------------
   Before starting, the program simulates the WHOLE QUEUE IN ORDER and says
   how many files fit, which is the first one left out, and how much would be
   missing on its turn. It warns; it does not block.

   And the file that does not fit NEVER STARTS. The queue used to announce
   "FILE 2/2", run the whole diagnosis (~20s) and only then discover 72 GB
   were missing. The refusal was always correct; the ORDER was wrong. The
   check moved to before the file is announced: it opens no block, creates no
   temp folder and never appears as "converting" for a single second.

   The factor lives in one place now (1.6x when the video does not leave the
   container, 3.15x when dovi_tool will touch it), and a P5 no longer pays
   3.15x - it does not go through dovi_tool at all.


 10. BEHAVIOUR FIXES
 --------------------------------------------------------------------------
   - "Keep" on the subtitle really turns the OCR off
   - The audio track name is the codec, not the track_name
   - A truncated output does not count as finished (cut at 60%)
   - An interrupted measurement becomes "EL not measured", in amber
   - "MAIN AUDIO" now says whose choice it is: the program IGNORES the file's

   - Discarding extra audio and subtitle tracks became a green seal:
     discarding is an action
   - One thing, one text: a single source for the Dolby Vision wording


 11. TEST BATTERY: 99 -> 497
 --------------------------------------------------------------------------
   Families that change what it is:

   - STRUCTURAL - fails a window function called inside a runspace, and
     requires every seal the engine produces to have its own branch in the
     window
   - EXECUTING - loads the real function and runs it against real numbers
     from the logs (the disk maths, the colour scale, the translation rules,
     the P5 path, the PGS subtitle choice with Troy's real track list, and
     the time calibration)
   - LOOKING AT ITSELF - fails if the battery itself had an execution error,
     and forbids a block comment that closes early

   The installer family was rebuilt too. The most valuable test in it READS
   the .ps1 files, collects every path under tools\ the code actually uses,
   and fails if any of them is in the .iss Excludes. That test is what caught
   DeeZy's ffmpeg being excluded WHILE the engine still called it - it would
   have compiled green and broken audio on the user's machine.

   Placebo tests were fixed too: one demanded frozen August versions and
   passed through a missing file; another read only half the versions and
   compared empty strings.


 WHAT THIS VERSION STILL DOES NOT DO, and it is written inside the program
 --------------------------------------------------------------------------
   - It does not measure the base layer's real brightness. The Simple/Complex
     split is a comparison against the declared master peak: a good
     indication, not a proof.
   - It does not regenerate the RPU's L1 for the base layer brightness. That
     would be the real fix for Complex FEL. No dovi_tool mode does it.
   - It does not keep the discarded EL.
   - It does not read the whole film during analysis - the reading is sampled
     from short pieces (five up to one hour, seven up to two, nine up to
     three, eleven above that).
   - It does not convert Profile 5 to 8.1 (its path is MP4).
   - It does not delete or alter your original file.
